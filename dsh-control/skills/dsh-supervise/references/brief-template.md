# 任务书模板

主控照这个写进项目计划文档（默认 `<项目>/docs/plan.md` 的一节），尖括号处填实。长工看不到主控和用户的对话，任务书必须自带全部背景。

```markdown
## <任务名>（主控下发，<日期>）

### 用户原话
<逐字引用用户的要求和以前定过的相关决定，以此为准>

### 终态
<做到什么样算完：可以核对的状态，例如「新版装进应用程序、14 项都有截图证据、全部检查通过并已推送」>

### 清单
每项写清怎么验收。★ 表示做完后要通知主控亲自验。
- [ ] 1. <内容> —— 验收：<命令、截图位置或检查方法>
- [ ] 2. ★ <内容> —— 验收：<…>

### 不做的事
- <明确排除的范围和以前否决过的做法>

### 需要用户决定
（长工遇到要用户操作或拍板的事写在这里，写清为什么要、要做哪几步）

### 长工规矩
- 主控会话：<主控会话编号>。汇报方式：`dsh-control notice <主控会话编号> '<内容>' --summary '<一行摘要>'`；主控在另一台机器时加 `-H <主控所在机器>`（会话里有 `skills.dsh_control` 时用 `notice` 函数，`host=` 同理）。
- 叫醒主控很贵，只有三种事用上面的写法：★ 项做完、任务书有错或做不到、需要用户的事。开工回执、顺手发现、更正、进度这类只让主控知道的，命令末尾加 `--quiet`（只放进主控上下文、不叫醒）；能写进本文件的就写进本文件，不发通知。
- 开工第一件事就用 create_goal 建目标（建不了就 quiet 通知主控，接着干活，主控会补一条消息让你建）：objective 写上面的终态，max_goal_rounds 设 <段上限，默认 10>。到上限会自动停下，这是正常的，主控会让你续段。
- 一项一项做。每项完成前跑全套检查：<列出命令>。全过才勾选、写证据（命令结果摘要、截图路径、提交号）、提交推送。
- ★ 项做完就汇报主控，发完不等回复，接着做下一项。
- 需要用户的事：写进「需要用户决定」，汇报主控，跳过这一项先做别的；只剩这类事时，用 update_goal pause 并写原因，然后停下。
- 不准开着目标等主控或用户：要等就 pause。
- 发现任务书有错或做不到：汇报主控说清原因，不自己改范围。
- 收到主控的插话或打回：照做；打回的项去掉勾重做。
- 全部做完：跑全套检查、确认已推送，用 update_goal complete，最后一轮逐项列出证据。
```

派单消息可以直接写「读 `<项目>/docs/plan.md` 的「<任务名>」一节，照其中的长工规矩开工」；任务书还没提交时把全文放进消息。
