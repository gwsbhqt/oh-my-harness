# dsh-supervise

主控 + 长工：用户只和主控（当前会话，高级模型）说话；粗活交给一个独立的长工会话（快档模型），长工可以在本机，也可以在另一台机器的 DSH 上。两边都是完整会话、各有自己的目标，用户随时能打开长工会话看或插话。主控等长工时挂起自己的目标、不空转，靠事件叫醒，不靠定时巡检。

省额度的前提是**主控醒一次很便宜**：每次叫醒，主控都要把自己整段上下文读一遍。例如用上下文 65 万～79 万的长会话当主控，85 分钟叫醒 25 次，就可能比三个长工合起来多花一倍用量。所以主控必须是专门开的短会话（第 0 步），长工只在需要主控拿主意时叫醒它。

所有动作走 `dsh-control`。会话里有 `skills.dsh_control` 就调它（函数名、选项与命令行同名，连字符换下划线，见 dsh-control 技能）；没有就用命令行 `dsh-control … --json`。主控自己的会话编号在环境变量 `DSH_SESSION_ID`。

## 什么时候用

- 用：活多、要跑很久、大部分是照清单做；每项验收能用命令、截图或文件核对。
- 不用：一两轮能做完的小事、每一步都要高级模型判断的事（设计取舍、疑难排查）。这些主控自己做。
- 长工在另一台机器时：对长工的所有命令都加 `-H <机器>`（Python 用 `host=`）；`--notify self` 照写，由本机后台观察进程盯远端、做完叫醒主控；长工汇报用 `dsh-control -H <主控所在机器> notice …`，机器名取对面 `dsh-control hosts` 里的名字；兜底检查加 `--host <机器>`。

## 两个目标

| | 主控 | 长工 |
|---|---|---|
| 目标内容 | 总目标：用户要的终态和验收标准 | 任务书里的这一段 |
| 等对方时 | `update_goal` pause（原因写「等长工：…」），被叫醒的那一轮能自己 resume、complete | 不许开着目标干等：要等主控或用户就 pause 并写原因 |
| 轮数上限 | 按需 | 分段，默认每段 10 轮，到上限停下等主控续段 |
| 完成 | 主控亲自核验后 | 长工自查通过后；主控核验不过就打回 |

为什么长工必须 pause：开着目标「等主控确认」会每几秒空转一轮（例如一小时空转约 30 轮）。

## 叫醒主控的三种事件

| 事件 | 谁发 | 怎么到主控 |
|---|---|---|
| 长工停下：做完、到段上限、自己 pause、提问、失败或中止 | dsh-control | 主控给长工发消息都带 `--notify self`；同一个长工只留一条在等的通知，重复带不会多送。长工真做完（口径同 `wait --settled`）送一次；提问另送提醒 |
| 长工主动汇报：只限 ★ 项做完、任务书有错或做不到、需要用户的事 | 长工 | `dsh-control notice <主控> '内容' --summary '一行摘要'`，发完不等回复继续做 |
| 长工卡死、主机/会话连不上、兜底检查自己出错 | 兜底检查脚本（不调模型） | `notice` 主控；同一次中断只在开始、到期未恢复、恢复这三个时刻各叫一次，重复失败只写日志不叫醒 |

其余要让主控知道、但不用它马上拿主意的事（开工回执、顺手发现、更正一个数字、进度），长工用 `notice … --quiet`：只放进主控上下文、不叫醒，主控下次醒来一起看到。

只按这些状态判断，不读长工回复里的字猜它做没做完。做完通知里的「结束原因 completed」只说明那一轮正常结束，分不清做完和到上限：醒来一律先查长工目标。

## 流程

### 0. 开一个专门的主控会话

当前会话只为这件事新开、还很短（不超过 10 轮、没聊过别的事）时，它就是主控，跳到第 1 步。否则先做完定方向需要的探索（第 1 步），把结论写成交接，开一个新会话当主控：

```bash
dsh-control new <工作区名> '你是这次任务的主控，照 dsh-supervise 技能的流程做。<交接：用户原话、已定的决定和否决过的做法、探索结论、终态和验收标准、任务书草稿或它的路径>' --tier normal --json
```

交接要自带全部背景，新主控看不到原会话。原会话告诉用户：「以后到『<新主控标题>』那个会话里跟我说」，然后结束本轮，不再参与；原会话有目标就 complete（终点写成「已交给新主控会话」）。新主控从第 2 步开始，由它派长工，长工的通知只叫醒它。

### 1. 探索、定方向（主控）

只做定方向所需的探索：读代码、看参考、核对用户以前的决定。结论写进任务书，不把探索交给长工重做，也不在主控这边干粗活。

### 2. 写任务书

照 [任务书模板](references/brief-template.md) 写进项目仓库的计划文档（默认 `<项目>/docs/plan.md` 里一节），把主控会话编号、段上限、要主控亲自验的 ★ 项填好。任务书是两边共用的进度表：长工做完一项勾一项、写证据，主控醒来只看它和提交的变化。

### 3. 派单

长工通常用快档：先 `dsh-control pick fast` 看当前选中的模型。也可以用 `--model provider/model --effort high` 直接指定模型和推理等级，不一定走档位。新任务开新会话；已在跑的长工追加任务用 `send`，不新开。

长工会话要从工作区名开，界面才会把它和主控归在同一组；用绝对路径开会落到「未分组」。在独立工作目录（git worktree）里干活的，开好再切目录、再发任务：

```bash
dsh-control new <工作区名> --tier fast --json                  # 不带消息，只建会话，拿 sessionId
dsh-control cwd <长工> <工作目录绝对路径> --json               # 不用独立工作目录就省掉这步
dsh-control send <长工> '<任务书全文，或「读 <计划文档> 的 X 节照做」>' --notify self --json
```

在 Python 内核里用 `bash` 跑这些命令时，消息用 `shlex.quote(msg)` 拼进去；会话里有 `skills.dsh_control` 就直接把消息当参数传。不要用 `json.dumps`：它把中文转成 `\u` 转义，双引号里的反引号还会被 shell 当命令执行，路径就丢了。

跨机器就在每条前面加 `-H <机器>`，其余不变；跨机器不能用 `chat --notify self`。保存回执里的 `sessionId` 和 `since`，回执的 `data.notify` 有 `watchId` 才算通知登记上了，有 `error` 就别重发，改用 `wait --settled` 自己等。然后挂兜底检查（持久后台服务，DSH 重启后自动接回；`--quiet` 让它的常规输出不叫醒主控，只有它发的 notice 才叫醒）：

```bash
dsh-control monitor "$DSH_SESSION_ID" --cwd <项目绝对路径> --label 'dsh-supervise 兜底检查' --quiet \
  --command "python3 -I $HOME/.agents/skills/dsh-supervise/scripts/watchdog.py --lead $DSH_SESSION_ID --worker <长工编号>"
```

记下返回的任务编号。多个长工就重复 `--worker`，一个兜底检查盯全部；长工在另一台机器就在命令里加 `--host <机器>`（一个兜底检查只盯一台机器）。卡死阈值默认 30 分钟（`--stall-minutes`），长工有超过半小时的构建或测试时调大；断线后多久再提醒一次默认 15 分钟（`--outage-minutes`）。

脚本自己把输出分成两路：需要主控看的事件（卡死、断线、恢复、检查器出错）写 stdout，重复失败和每轮诊断写 stderr。用 `dsh-control monitor --quiet` 挂时只有 notice 会叫醒主控；直接用 `monitor` 工具挂时用 `delivery: inject` 就行，不需要再写 `ignore_stdout_lines` 或手工过滤。同一次主机/会话断线只在开始、超过 `--outage-minutes` 仍未恢复、恢复这三个时刻各发一次 notice，其余每轮只进日志；恢复通知会请主控补查中断期间没看到的结果，脚本也会把中断时长补回卡死计时，短期网络故障不会被当成任务失败或丢失。

派单后的下一次醒来先查长工有没有目标（`dsh-control goal <长工>`）。长工开工那一轮如果被 DSH 重启打断，续上的那一轮不是用户消息开的，系统不让它建目标；这时主控 `send` 一句「现在用 create_goal 建目标，objective 照任务书写」，这条消息开的一轮能建，不用作废会话重开。

最后主控有目标就 pause，`blocked_reason` 必须写「等长工：<在等什么>」，不能留空。简短告诉用户派了什么、怎么验收，结束本轮。

### 4. 被叫醒时

先看事实，不重读长工整段对话：

```bash
dsh-control goal <长工> --json          # phase、roundsStarted/maxGoalRounds、blockedReason.code
dsh-control status <长工> --json        # running、queued、questions
git -C <项目> log --oneline <上次看过的提交>..HEAD; git -C <项目> diff <上次>..HEAD -- docs/plan.md
dsh-control last <长工> --chars 4000 --json   # 需要时才看最后一轮
```

| 情况 | 怎么认 | 主控做什么 |
|---|---|---|
| 说全部做完 | 长工目标 `complete`，或汇报「全部完成」 | 亲自核验：跑任务书里的验收命令、看截图和产物、查是否推送。不对就 `send` 打回（写清哪项、为什么、怎么算过）；对了进第 5 步 |
| ★ 项做完 | 主动汇报 | 只验这一项。有问题用 `send --now` 插话打回，不打断它手上的活 |
| 到段上限 | `blockedReason.code == round-limit` | 对比计划文档：这一段有推进就 `send` 让它「用 update_goal edit 把 max_goal_rounds 加 10，再 resume，继续」；没推进或在重复，看最后一轮，纠偏或停下 |
| 长工自己 pause | `blockedReason.code == model-paused` | 核实原因。主控能解决的直接给办法让它 resume；要用户的，用人话转告用户并写清步骤，长工保持暂停 |
| 停下提问 | `questions` 非空或收到提醒 | 主控能答就 `dsh-control answer`；要用户定的转告用户 |
| 失败或中止 | 通知里的结果 | 看报错，必要时重新派 |
| 兜底检查的通知 | 兜底通知 | 说卡死就看它最后一轮和后台任务，确实卡住用 `send --interrupt`；说连不上/恢复就按通知补查中断期间的结果，不重派、不当任务丢了；说检查器出错就按报错修，修好前没人盯长工 |
| 长工没有目标 | `goal` 查不到目标 | `send` 让它现在建（见第 3 步），不重开会话 |
| 重启后的提醒 | DSH 重启通知 | 查长工目标已恢复就不用管 |

每次处理完：给长工的每条消息都带 `--notify self`；主控目标重新 pause 并写原因；回复简短，用户没问就不汇报细节。只有一两行就能改完、改完不用再验的小事，主控才自己动手。

### 5. 收尾

1. 按总目标逐项亲自核验关键项，跑全套检查，确认已提交推送。
2. 停掉兜底检查：`dsh-control kill-jobs <第 3 步记下的任务编号>`。
3. 长工目标应为 `complete`；不是就让它收口。
4. 主控 resume 再 complete 自己的目标。
5. 向用户汇报：完成了什么、主控亲自核验了哪些、没做的和原因、要用户做的事。

## 省额度的规矩

- 主控上下文要短：用户在长会话里提出这类任务，就按第 0 步换新会话当主控。主控自己也变长了（例如超过 20 万）时，同样交接给新主控。
- 少叫醒：任务书写明只有 ★ 项、任务书有错、需要用户的事才叫醒，其他用 `--quiet`。★ 只标关键、有风险、长工容易糊弄的项，不是每项都标。
- 醒来只做这一件事：只是确认收到的，一句话结束本轮，不顺手查别的。
- 主控醒来先看状态、计划文档和提交差异；只在需要时读长工最后一轮。
- flash 会虚报完成、跳过全套检查：主控验收必须拿自己的证据，不信长工的汇报。
- 需要用户的事由长工记进计划文档「需要用户决定」、通知主控，然后先做别的项；只剩这类时才 pause。主控统一转告用户，不让长工直接问用户。
- 不定时巡检：方向检查跟着 ★ 项和段上限走，按进度看，不按钟点看。
