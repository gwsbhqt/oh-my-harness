# 任务隔离划分边界，不会再造一个桌面

一个示例长工在检查 `https://example.com` 页面，另一个长工在同一浏览器编辑别的页面。双方都需要已有登录状态，同时还有人在用电脑。给长工分配不同会话是必要的，但还不够：它们仍能接触同一浏览器配置、原生窗口、账号和远程文件。

操作前要明确几件事。哪台机器或哪个浏览器接收操作？具体选中了哪个标签或原生窗口？本任务创建了哪些资源，结束时可以清理哪些？发布、删除或修改账号仍需相应授权。

本文描述有源码依据的行为，不是新一轮真实环境验收。[浏览器说明](../../skills/browser-use/README.md)、[桌面说明](../../skills/computer-use/README.md)和[远程说明](../../skills/remote-host/README.md)规定支持的平台与前提条件。

## DSH 提供什么，技能补充什么

DSH 提供对话、工具和会话标识。桌面技能用任务范围记录原生应用的归属。浏览器技能则让调用方选择浏览器连接，并在每次网页操作或调试时传入目标标签的编号。macOS 管理原生窗口和输入权限，OpenSSH 管理远程认证与传输。

## 在浏览器里保留各自的标签编号

两个任务即便打开同一网址，也可以各自保留 `tab_open` 返回的 `tabId`。读取快照、点击控件或读取网络请求时，沿用本任务的连接和编号。已有标签可通过 `tabs_list()` 查看，从选定记录的 `id` 取得编号。对话分支若需要自己的标签，就打开新标签并记录回执。重新连接后先核实目标，标题、网址或当前可见页都可能相同。[浏览器示例](../browser-use.md)

## 不同标签仍然共享账号状态

Cra 网页使用 Cra 官方 MCP。Chrome 连接已开启调试的指定实例。两端都可以通过 Google 的 Chrome DevTools MCP 调试选定标签。需要隔离登录状态时，应先准备使用独立资料的浏览器实例，再连接它。同一资料中的两个标签可能共享账号和网站设置，在其中一页退出登录会影响另一页。

调用方记录本任务打开的标签，结束时用 `tab_close(tabId=...)` 逐个关闭。退出 Python 的 `async with` 结束工具连接。借来查看的标签留给原使用者。[浏览器连接和收尾](../../skills/browser-use/src/browser_use/browser.py)

## 原生窗口不能变成独立桌面

桌面工具面对不同问题。有的操作直接作用于辅助功能元素，有的依赖事件投递与焦点。真实前台仍只有一个，人可以在两次检查之间改变它。

稳定窗口引用包含窗口标识、进程标识、进程启动时间和应用身份。[Swift 执行程序](../../skills/computer-use/bin/computer-use.swift)检查原进程代次和确切窗口是否仍有效，拒绝用相似标题或位置替代。元素检查也会确认其属于绑定窗口。

对非浏览器应用，工具记录任务归属和会变化的授权凭证。交接和释放会使旧凭证失效。浏览器应用则使用任务窗口和短操作锁，允许不同窗口协作，而不占有整份共享浏览器。键盘、粘贴、菜单和基于事件的鼠标操作使用共享桌面输入锁。浏览器输入还检查前台应用、准确焦点窗口，以及相关场景中的焦点元素。

这些措施减少协作调用方之间的争抢，但不能阻止人或同账号其他程序在检查后立刻切焦点。长输入会复查焦点，变化时停止。如果输入可能已经发出，结果就是未知。[桌面规则](../../skills/computer-use/references/common.md)明确说明仍然存在的争抢风险。[引用约定测试](../../skills/computer-use/tests/test_contract.py)检查是否拒绝其他任务、其他窗口和旧凭证。

辅助功能和屏幕录制权限属于目标上的实际进程。版本探测成功，既不证明权限，也不证明应用可控。部分定向输入还使用私有 macOS 接口，因此系统变化可能使其失效。不支持的定向操作会失败，不会悄悄改为全局输入。系统身份确认和敏感应用限制是额外边界，不能靠任务名绕过。

## 远程意味着真实目标

computer-use、remote-host 和 dsh-use 共用[目标解析](../../skills/_shared/agentkit/remote/target.py)和 [SSH 传输](../../skills/_shared/agentkit/remote/ssh.py)，各自记住默认机器。显式指定的目标对本次调用优先，已绑定的桌面对象保留原来选择的机器。未知别名、损坏的选择状态、缺远程工具和连接失败都会报错。remote-host 要求明确的远程目标。

远程脚本使用系统 SSH 客户端和已配置的认证。通过 SSH 转发的桌面和会话控制命令会先核对目标端的能力。browser-use 独立选择浏览器与调试地址。要在另一台机器上操作原生对话框，还需为 computer-use 另行指定确切机器和窗口。[公共传输规则](../../skills/remote-host/references/transport.md)

SSH 不会把脚本放进沙箱。它使用已认证账号的真实访问权。同账号的两个长工仍能修改同一文件。[复制和验证规则](../../skills/remote-host/references/copy-verify.md)说明放置前暂存和内容检查。条件替换可以比较预期 SHA-256，检测中途修改。传输成功只证明送达，内容和服务检查才证明目标结果。

## 不确定操作之后，先观察

超时不会撤销操作。点击、输入或远程写入的结果不确定时，先观察原目标。在同一标签重新读取清单，就能检查丢失回复的提交是否已生效。原目标无法辨认时，先核对身份再继续。

有效检查应问：预期页面是否变化，是否只有目标窗口消失，传输字节是否一致，以及最终服务能否响应。子进程正常退出本身回答不了这些问题。

## 证据与测量

归档版的双标签实验使用两份相同的虚构清单，读回两个计数，并保留了截图和当时使用的步骤。[旧版实拍与复现说明](../browser-use.md#two-tabs) · [归档的任务隔离与测试](https://github.com/gwsbhqt/oh-my-harness/blob/archive/browser-use-before-mcp/docs/design/task-isolation.md)

核对当前版本时，可以用同一份示例创建两个标签，保存不同的 `tabId`。只修改一页后分别读回两页，再按编号关闭本任务的标签。记录浏览器版本、使用的实例、两个读数与实际关闭的标签。原生窗口的焦点和 SSH 目标的权限需要在各自环境另外核对。

可重复的发布测量应放在[测量结果](../../benchmarks/results.json)中。这里不推断任何耗时、吞吐或节省数字。目前有依据的结论是：明确身份和保守的失败规则，让任务之间的误操作更容易发现。账号、桌面焦点和真实远程权限仍然是共享的。
